# Dashboard overview API

User asks to consolidate the dashboard's many requests under /me and minimize quota. Implement locally without new dependencies or database changes.

`GET /me/dashboard/overview`, authenticated LEARNER only, Cache-Control private/no-store. Keep /me identity and /me/dashboard analytics compatible. Required programContext comes from getContext; then existing progress, availability, roadmap, analytics, engagement services run in parallel. Fetch Intermediate topics only for that active program. Each dependent section returns `{status:'ready',data}` or `{status:'error',error:{code,status}}`; never serialize raw internal messages. Authentication failures must propagate, not become partial successes. No active program skips program-dependent calls.

Shared contract: `dashboardOverviewSchema` / `DashboardOverview`, properties programContext, progress, availability, roadmap, analytics, engagement, topics. Reuse DTO schemas; lift progress schema from web into contracts. No internal HTTP fan-out or duplicate calculations. Aggregation reduces network requests; it does not promise fewer SQL queries or one database snapshot.

Page initial mount makes exactly one overview request, with cancellation and stale-result protection. Continue supporting focused retry APIs and weekly-target/session mutations. IntermediateTopicPicker accepts optional prefetched topics/failed flag; dashboard uses them so it does not immediately re-request the same list, but standalone picker and retry retain existing endpoint. Preserve legacy availability422 tolerance for Intermediate and no-active-program handling. IELTS feature-specific cards and layout authentication remain independent scope; do not claim all browser requests disappear.

Tests first: orchestration/scope, partial failures, auth propagation, no-program/no-topics, HTTP role/no-store; web single request, analytics retry preserves resume, no-program and Intermediate eligibility independent of availability422. Focused suites, types/lint/API build, runtime health; one bounded review. No broad refactors/full-suite reruns unless focused evidence warrants them. Local commits only.

Focused progress/availability retries retain healthy sections and check program context before and after fetching. A changed enrollment revision triggers a fresh overview. The page shares an in-flight request during StrictMode effect replay, aborts it on real unmount, and ignores late responses. No cross-user/global response cache is added.
