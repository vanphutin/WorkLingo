# WorkLingo UI internationalization

WorkLingo supports `vi` (the new-user default) and `en`. UI language is independent of the language being learned. Existing URLs are unchanged.

## Architecture

`apps/web/src/i18n/locale.ts` owns the supported UI locales, validation, default and browser cookie names. `translator.ts` wraps next-intl's ICU `createTranslator` with type-checked keys, interpolation, pluralization and English missing-key fallback. Unknown runtime keys render `namespace.key`; the repository gate detects catalog mistakes before release. See the [official next-intl core API](https://next-intl.dev/docs/environments/core-library).

`provider.tsx` holds the display locale without keying or remounting its children. A locale change updates the shared React context and `document.documentElement.lang`, preserving forms, drafts, answers, recording, enrollment and session identifiers. Components import their own namespace catalog. Both dictionaries for that feature travel in its chunk, permitting immediate switches without loading every application's messages into the root provider.

`server.ts` uses asynchronous Next.js cookies and request-local React cache. SSR and metadata prefer the authenticated `/me` locale over the guest cookie. Internal API calls forward only the session cookie, use `cache: no-store`, and have a three-second timeout. No user locale is cached across requests. When authentication cannot be checked because the API is unavailable, SSR uses the validated cookie, then `vi`; protected layouts continue their existing authentication checks. `LocalizedPageTitle` updates the browser title during client switches without a route refresh. Existing page metadata titles are also localized on SSR.

The app root always supplies the resolved locale. Standalone component tests/embeds without the provider retain legacy English to make their language explicit and keep existing test fixtures useful; this fallback does not determine the application default.

## Add messages

Create a paired catalog in `apps/web/src/i18n/messages/<namespace>.ts`:

```ts
export const exampleMessages = {
  en: { welcome: 'Hello {name}', count: '{count, plural, one {# lesson} other {# lessons}}' },
  vi: { welcome: 'Xin chào {name}', count: '{count, plural, other {# bài học}}' },
} as const;
```

Use `const t = useT('example', exampleMessages)` and render `t('welcome', {name})`. Catalogs use flat semantic keys; do not put dot-separated keys inside these maps. Store error/message descriptors or original causes in state so a visible message can be translated again after switching. Never store a translated label as a business status, API value, identifier, CSS selector or React key.

Server components use `getServerT(namespace, catalog)` or the pure `translate(locale, namespace, catalog)`. Use `formatNumber`, `formatDate`, `formatRelativeTime`, or equivalent `Intl` with the active locale. Keep timestamps unchanged; supply an existing user's timezone when available. Otherwise client formatting uses the browser timezone. UI locale must not replace speech locale `en-US`.

## Preference policy

1. A current explicit selection wins in the mounted UI.
2. An account's server preference wins on login and SSR/reload.
3. A guest uses the validated `worklingo_locale` cookie.
4. Missing/invalid preferences use `vi`.

Guest switching writes a one-year, root-path, SameSite=Lax cookie (Secure on HTTPS). A blocked localStorage does not prevent switching or cookie persistence. Login does not overwrite an existing account's preference with another account's browser selection. Registration may explicitly send the guest selection; old clients still default to `vi`. Logout leaves the current display locale available for the guest; the next login adopts the next account's preference.

Authenticated accounts use `GET /api/v1/me/preferences` and `PATCH /api/v1/me/preferences` with `{locale: 'vi' | 'en'}`. The existing global auth and input-validation pipeline applies. Unexpected body fields such as `userId` are rejected. Optional `x-worklingo-account-id` binds frontend writes to the account active when the selection was made; a request made with a different current session returns `409 ACCOUNT_CHANGED` without updating either account. Existing API clients without this header remain supported.

Persistence reuses `LearnerProfile.locale`. Reading an Admin without a profile returns `vi` without mutation. Its first explicit save creates a default profile and sets locale; it creates no enrollment, learning session, assessment or progress. No database migration was added. `AuthUser.locale` and `RegisterInput.locale` are optional additions to existing contracts for backward compatibility; the server always returns a supported locale.

Writes are serialized. A successful response records the persisted language; a failed final write rolls back to that language, broadcasts the persisted value to other tabs and shows a localized error. Account identity and generation checks discard stale responses. Focus refresh cannot replace an explicit save still in progress. Browser storage events contain only `{userId, locale, nonce}`, are accepted only for the current account/guest, and never cause another server write. On focus, a signed-in tab checks `/me` to pick up another device's preference. If the session expires, its locale identity is cleared; if another account is discovered, the root reloads to resolve account data and language together, instead of binding the old workspace to the new account. Ordinary language switching does not reload. This is synchronization on login/reload/focus, not a persistent websocket connection.

## Shared switcher

`components/language-switcher.tsx` is reused in public/auth, learner/admin navigation and Settings. A native select provides keyboard behavior, selected state, language autonyms, localized accessible label, visible focus and a 44px target. It displays a localized saving state and error. Language names deliberately retain their own language; no flag-only icons are used.

## Educational boundary

Translate fixed system UI, system instructions, button labels, enums displayed as UI, empty/loading/error states and form validation. Preserve lesson passages, transcript, English examples, questions, options, answers, authored lesson names/objectives, audio preview, user-entered text and user names. Where appropriate, English educational wrappers use `lang="en"`; existing Vietnamese explanations remain Vietnamese.

API machine error codes, HTTP statuses, request identifiers, payloads and diagnostic codes remain unchanged. `i18n/errors.ts` maps known error categories for display and uses a safe generic localized fallback. Admin validation keeps original technical diagnostics accessible where supported, alongside localized issue summaries. It does not translate imported source or immutable published lesson versions.

Future curriculum localization should use separately reviewed variants keyed by lesson-version ID, locale and field, with source/provenance and publication validation. It must not rewrite the published lesson snapshot.

## Validation and inventory

```powershell
pnpm i18n:check
pnpm test:i18n
node scripts/i18n-check.mjs --inventory
pnpm --filter @worklingo/web exec vitest run src/i18n
pnpm --filter @worklingo/api exec vitest run test/integration/locale-preferences.integration.spec.ts
pnpm --filter @worklingo/web e2e --project=i18n-desktop --project=i18n-mobile
pnpm verify
```

The catalog validator checks paired keys, ICU syntax, matching interpolation arguments and statically referenced unknown keys. It reports candidate unused keys, including references through feature hooks and literal enum/message maps. Dynamic key construction and exact lookup of server prose can make these candidates false positives; review before removing any key. It does not claim exhaustive runtime reachability.

`docs/I18N_STRING_INVENTORY.json` inventories current source literals and dynamic educational/user boundaries. It records system UI, learning content, user-generated content, system-error identifiers and technical identifiers. This is a static audit aid, not an automatic translator or proof that every API prose branch is localized. Native language names, the brand and CEFR/version notation are intentional exclusions.

English regression E2E journeys explicitly configure an English guest cookie or registration locale; new i18n projects use empty guest state to verify Vietnamese defaults. Tests never change production default behavior. All database integration/E2E writes use the repository's disposable schema harness.

## Add a locale later

Add the validated locale to the shared preference schema, web `UI_LOCALES`, formatting map, every namespace dictionary and the switcher's language list. Extend validator locale iteration and contract/unit/E2E tests before enabling it. The route architecture and component APIs need no rewrite. A new locale is a reviewed catalog and validation change, not a runtime AI translation feature.
